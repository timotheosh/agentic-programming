* Purpose

This document is a copy-ready template for a Hermes Agent development workflow in which:

1. =test-designer= independently translates requirements into executable behavioral tests and proves RED.
2. =implementer= uses ACD principles to produce the smallest coherent implementation that makes the tests GREEN.
3. =correctness-reviewer= checks requirements, tests, coverage, and behavior.
4. =structural-reviewer= checks duplication, contracts, schemas/specs, complexity, and maintainability.
5. =flow-documenter= documents the final approved runtime flow in Draw.io.

The two reviewers form a fail-closed AND gate. Neither reviewer may edit files. Each implementation slice must pass that gate, but =flow-documenter= runs only once: after every planned slice is complete and both reviewers approve the final integrated revision. The overall task is complete only when that final flow documentation is complete.

Unlike the companion Claude Code workflow, Hermes agents are independent =hermes chat= processes that do not share conversational context. All communication flows through committed artifacts on disk. Each agent can run with its own model, provider, turn budget, and toolset — configured in a single YAML file.

* Operating model

#+begin_example
Requirements and planned slices
              │
              ▼
  ┌──── repeat for each slice ────┐
  │ test-designer → verified RED  │
  │              │                │
  │              ▼                │
  │ implementer + ACD → GREEN     │
  │              │                │
  │              ▼                │
  │ correctness + structural      │
  │ reviewers → dual approval     │
  └──────────────┬────────────────┘
                 │ all slices complete and
                 │ final revision approved
                 │
                 ▼
          flow-documenter (once)
                 │
                 └── docs/<feature>-flow.drawio
#+end_example

Reviewers may run concurrently after implementation, but they must receive the original requirements before the implementation report so the implementer's narrative does not define correctness. Concurrent reviewer execution requires =--worktree= isolation; sequential execution is safe on the shared working tree.

The orchestrator (=orchestrator.py= or an =execute_code= block) coordinates all stages. It never pipes raw agent output into the next agent — only committed files and written artifacts. Every agent invocation captures exit status, stdout, stderr, and elapsed time.

You are the independent Test Designer. Convert the original requirements into executable behavioral evidence before production implementation begins.

Read, in order:
1. the original requirements;
2. `.ai/workflow/current.md` if present;
3. existing tests and test conventions;
4. nearby production interfaces only as needed to design externally meaningful tests.

Before adding anything, search the repository for reusable fixtures, factories, mocks, fakes, helpers, builders, test containers, and harnesses. Reuse or extend them when coherent. Do not introduce duplicated test infrastructure or brittle implementation-detail coupling.

Write focused behavioral/acceptance tests for:
- every stated requirement and acceptance criterion;
- material boundary values and failure paths;
- calculations and business rules where errors would be meaningful;
- data-contract behavior visible at important boundaries.

Do not attempt exhaustive low-level unit testing and do not dictate private implementation structure. The implementer may add local unit tests later.

You may modify tests and shared test-support code. You must not modify production implementation files or implement missing production behavior. If a test cannot be written without a production API decision that materially changes public behavior or architecture, stop and report the decision instead of inventing it.

Run the smallest relevant test command and demonstrate RED. A valid RED is a clean assertion or behavior failure attributable to the missing requirement. Syntax errors, missing dependencies, broken fixtures, test-discovery failures, and unrelated failures are invalid; repair test infrastructure and rerun until the intended failure is observed.

Write `.ai/test-plan.md` with:
- requirement identifier and summary;
- requirement-to-test mapping with file and test name;
- edge and failure cases;
- reused or extended test infrastructure;
- exact command run and concise RED evidence;
- intentionally uncovered behavior and rationale;
- assumptions, ambiguities, and blockers.

Update your stage in `.ai/workflow/current.md`. Stop at verified RED. Return a concise handoff naming the artifacts and the intended failing behavior; do not declare implementation complete.

## Workflow-specific implementation constraints

Never delete, skip, weaken, or rewrite an independent behavioral test merely to get GREEN. If a test contradicts the requirement or encodes an invalid assumption, stop and report the exact test, requirement, conflict, and proposed resolution to the orchestrator.

Coverage and contract requirements:
- Give calculation and business-rule functions meaningful behavioral coverage, including important branches and boundary cases. Raw line coverage alone is insufficient.
- Add implementation-specific unit tests when they add confidence without coupling to incidental structure.
- Give data crossing meaningful external, persistence, API, event, or domain boundaries an explicit contract.
- In Clojure, use `clojure.spec` or the repository's established schema library. Do not spec every trivial local value.
- In other languages, use the repository's established type, schema, or validation mechanism.
- Validate at boundaries and provide useful failure information.

Search the repository before introducing helpers, abstractions, schemas/specs, or test infrastructure. Remove duplication only when the shared concept is stable and the result is clearer.

Run the focused tests during development, then the complete relevant suite, linters/static checks, and the repository's coverage command when available. Do not claim GREEN if unrelated relevant tests fail.

Write `.ai/implementation-report.md` with:
- requirement and revision/diff reviewed;
- files changed and why;
- test and check commands with results;
- meaningful coverage for calculation/business logic;
- specs, schemas, types, or validators added/changed;
- existing code reused and duplication considered;
- assumptions, risks, and unresolved issues.

Update `.ai/workflow/current.md`. Stop at GREEN and return the review packet. Do not approve your own work and do not invoke final documentation.

You are the independent Correctness Reviewer. You are read-only: do not modify files, fix findings, or expand scope.

Read the original requirements before reading `.ai/implementation-report.md`. Review the exact revision recorded in `.ai/workflow/current.md` and identify if the working tree changed afterward.

- omitted coverage is justified;
- the complete relevant suite is GREEN.

You MUST output a single JSON object wrapped in a code block, then stop. Do not write the file yourself — the orchestrator will save it. The JSON must be the LAST thing in your response.

  "verdict": "APPROVE",
  "revision": "<git commit sha or dirty-tree description>",

      "id": "C1",

      "evidence": "<concrete evidence and reproduction command>",
      "why": "<why it matters>",

  ]
}

* Copy into =orchestrator.py=

The orchestrator is a standalone Python script. Run it with =python .hermes/pipeline/orchestrator.py= or as an =execute_code= block inside Hermes. =PIPELINE_REQUIREMENTS_FILE= is mandatory (path to a requirements document relative to the project root). =PIPELINE_PROJECT= defaults to the current working directory. =PIPELINE_FEATURE= defaults to the requirements filename without extension.

Each agent runs as an independent =hermes chat= process. The orchestrator writes the prompt to a temp file (passed via =--query-file= — never shell-interpolated), spawns the process, captures exit code / stdout / stderr / elapsed time, and validates that the required artifact exists before proceeding to the next stage.

Reviewer verdicts are parsed from JSON code blocks. Malformed, missing, or non-JSON output is treated as =REQUEST_CHANGES= (fail closed). Verdicts are validated against the expected git revision to prevent stale approvals.

#+begin_src python :tangle .hermes/pipeline/orchestrator.py
"""ACD Pipeline Orchestrator for Hermes Agent.

PIPELINE_REQUIREMENTS_FILE=docs/spec.md python .hermes/pipeline/orchestrator.py

PIPELINE_REQUIREMENTS_FILE (mandatory) — path to a requirements doc, relative
    to the project root.
PIPELINE_PROJECT (optional) — project directory. Defaults to CWD.
PIPELINE_FEATURE (optional) — short label. Defaults to the requirements
    filename without extension.

Or inside a Hermes execute_code block — the hermes_tools import works there.
"""

from hermes_tools import terminal, read_file, write_file
import json, re, tempfile, os, time, subprocess, sys

try:
    import yaml
except ImportError:
    print("yaml not available — install pyyaml or use execute_code")
    sys.exit(1)


# ── Configuration ──

PROJECT = os.path.abspath(os.environ.get("PIPELINE_PROJECT", "."))

reqs_file = os.environ.get("PIPELINE_REQUIREMENTS_FILE", "")
if not reqs_file:
    print("PIPELINE_REQUIREMENTS_FILE is required", file=sys.stderr)
    sys.exit(1)
reqs_path = os.path.join(PROJECT, reqs_file)
with open(reqs_path) as f:
    REQUIREMENTS = f.read()

FEATURE = os.environ.get("PIPELINE_FEATURE", "")
if not FEATURE:
    FEATURE = os.path.splitext(os.path.basename(reqs_file))[0]

CONFIG_PATH = f"{PROJECT}/.hermes/pipeline/config.yaml"
with open(CONFIG_PATH) as f:
    config = yaml.safe_load(f)

AGENTS = config["agents"]
SETTINGS = config.get("settings", {})


# ── Agent Runner ──

def run_agent(role, task, extra_context="", worktree=False):
    """Spawn a Hermes agent as an independent process.

    Returns dict with exit_code, stdout, stderr, elapsed_s, success, timeout.
    """
    cfg = AGENTS.get(role, {})
    model = cfg.get("model")
    provider = cfg.get("provider")
    max_turns = cfg.get("max_turns", 100)
    run_budget = cfg.get("run_budget")
    reasoning = cfg.get("reasoning")
    toolsets = cfg.get("toolsets")
    timeout = SETTINGS.get("agent_timeout_seconds", 900)

    # Load role prompt
    prompt_file = f"{PROJECT}/.hermes/pipeline/prompts/{role}.md"
    with open(prompt_file) as f:
        system_prompt = f.read()

    full_prompt = f"""{system_prompt}

## Task
{task}

## Context
Project: {PROJECT}
Feature: {FEATURE}
{extra_context}
"""

    # Write prompt to temp file — safe: no shell interpolation
    with tempfile.NamedTemporaryFile(mode="w", suffix=".md", delete=False) as tf:
        tf.write(full_prompt)
        prompt_path = tf.name

    cmd = ["hermes", "chat", "--query-file", prompt_path,
           "--oneshot", "-Q", "--in", PROJECT,
           "--max-turns", str(max_turns)]
    if model:
        cmd.extend(["--model", model])
    if provider:
        cmd.extend(["--provider", provider])
    if run_budget:
        cmd.extend(["--run-budget", str(run_budget)])
    if reasoning:
        cmd.extend(["--reasoning", reasoning])
    if toolsets:
        cmd.extend(["--toolsets", toolsets])
    if worktree:
        cmd.append("--worktree")

    t0 = time.monotonic()
    result = terminal(command=subprocess.list2cmdline(cmd), timeout=timeout, workdir=PROJECT)
    elapsed = time.monotonic() - t0

    try:
        os.unlink(prompt_path)
    except OSError:
        pass

    return {
        "role": role,
        "exit_code": result.get("exit_code"),
        "stdout": result.get("output", ""),
        "stderr": result.get("error", "") if isinstance(result.get("error"), str) else "",
        "elapsed_s": round(elapsed, 1),
        "timeout": result.get("exit_code") == 124,
        "success": result.get("exit_code") == 0,
    }


# ── Review Verdict Parser ──

def parse_review_json(filepath):
    """Extract JSON verdict from a review artifact file.

    Returns parsed dict, or None if unparseable.
    """
    content = read_file(filepath).get("content", "")
    if not content:
        return None

    # Try fenced JSON code block first
    m = re.search(r'```(?:json)?\s*\n(.*?)\n```', content, re.DOTALL)
    if m:
        try:
            return json.loads(m.group(1))
        except json.JSONDecodeError:
            pass

    # Fallback: find a JSON object containing "verdict"
    m = re.search(r'\{[^{}]*"verdict"[^{}]*\}', content)
    if m:
        try:
            return json.loads(m.group(0))
        except json.JSONDecodeError:
            pass

    return None


def validate_verdict(verdict, expected_revision):
    """Check verdict is well-formed and targets the correct revision."""
    if verdict is None:
        return {"valid": False, "reason": "unparseable output"}
    if "verdict" not in verdict:
        return {"valid": False, "reason": "missing 'verdict' key"}
    if verdict["verdict"] not in ("APPROVE", "REQUEST_CHANGES"):
        return {"valid": False, "reason": f"invalid verdict value: {verdict['verdict']}"}
    if verdict.get("revision") != expected_revision:
        return {"valid": False, "reason":
                f"revision mismatch: {verdict.get('revision')} vs {expected_revision}"}
    return {"valid": True, "verdict": verdict["verdict"],
            "findings": verdict.get("findings", [])}


# ── Artifact Verifiers ──

class StageFailed(Exception):
    pass


def verify_artifact(path, description):
    if not os.path.exists(path):
        raise StageFailed(f"{description} not found: {path}")
    if os.path.getsize(path) == 0:
        raise StageFailed(f"{description} is empty: {path}")
    print(f"  OK: {description}")


# ── Pipeline ──

def run_pipeline():
    print(f"Pipeline: {FEATURE}")
    print(f"Project:  {PROJECT}")
    print(f"Config:   {CONFIG_PATH}")
    print()

    # ── Stage 1: Test Design ──
    print("─── Stage 1: Test Design ───")
    td = run_agent("test-designer",
        f"Convert these requirements into behavioral tests and prove RED:\n\n{REQUIREMENTS}")
    _report_agent(td)
    if not td["success"]:
        raise StageFailed("test-designer failed")
    verify_artifact(f"{PROJECT}/.ai/test-plan.md", "test plan")

    # ── Stage 2: Implementation ──
    print()
    print("─── Stage 2: Implementation ───")
    impl = run_agent("implementer",
        f"Make the tests GREEN.\n\nOriginal requirements:\n{REQUIREMENTS}")
    _report_agent(impl)
    if not impl["success"]:
        raise StageFailed("implementer failed")
    verify_artifact(f"{PROJECT}/.ai/implementation-report.md", "implementation report")

    # ── Stage 3: Reviews (sequential by default; add worktree=True for parallel) ──
    review_round = 0
    max_rounds = SETTINGS.get("max_review_rounds", 5)
    current_revision = _get_revision()

    while review_round < max_rounds:
        review_round += 1
        print()
        print(f"─── Stage 3: Review Round {review_round}/{max_rounds} ───")

        print("  Correctness review...")
        cr = run_agent("correctness-reviewer",
            f"Review correctness.\n\nOriginal requirements:\n{REQUIREMENTS}",
            worktree=SETTINGS.get("reviewer_parallel", False))
        _report_agent(cr)

        print("  Structural review...")
        sr = run_agent("structural-reviewer",
            f"Review structure.\n\nOriginal requirements:\n{REQUIREMENTS}",
            worktree=SETTINGS.get("reviewer_parallel", False))
        _report_agent(sr)

        # Parse verdicts
        verify_artifact(f"{PROJECT}/.ai/reviews/correctness.md", "correctness review")
        verify_artifact(f"{PROJECT}/.ai/reviews/structural.md", "structural review")

        cr_json = parse_review_json(f"{PROJECT}/.ai/reviews/correctness.md")
        sr_json = parse_review_json(f"{PROJECT}/.ai/reviews/structural.md")

        cr_valid = validate_verdict(cr_json, current_revision)
        sr_valid = validate_verdict(sr_json, current_revision)

        for label, result in [("Correctness", cr_valid), ("Structural", sr_valid)]:
            if result["valid"]:
                print(f"  {label}: {result['verdict']} ({len(result['findings'])} findings)")
            else:
                print(f"  {label}: FAILED — {result['reason']}")

        if all(v["valid"] and v["verdict"] == "APPROVE" for v in [cr_valid, sr_valid]):
            print()
            print("═══ DUAL APPROVAL — slice complete ═══")
            return True

        # Route findings to owners
        all_findings = cr_valid.get("findings", []) + sr_valid.get("findings", [])
        owners = set(f.get("owner") for f in all_findings if f.get("owner"))
        print(f"  Findings require changes from: {owners or 'unknown'}")

        # If test changes needed, re-run test-designer then implementer
        if "test-designer" in owners or "both" in owners:
            print("  → Re-running test-designer...")
            td = run_agent("test-designer",
                f"Address review findings and re-establish RED.\n\nFindings:\n"
                f"{json.dumps(all_findings, indent=2)}\n\n"
                f"Original requirements:\n{REQUIREMENTS}")
            _report_agent(td)

        if "implementer" in owners or "both" in owners or "test-designer" in owners:
            print("  → Re-running implementer...")
            impl = run_agent("implementer",
                f"Address review findings and re-establish GREEN.\n\nFindings:\n"
                f"{json.dumps(all_findings, indent=2)}\n\n"
                f"Original requirements:\n{REQUIREMENTS}")
            _report_agent(impl)

        current_revision = _get_revision()

    raise StageFailed(f"Exceeded {max_rounds} review rounds without dual approval")


def _report_agent(result):
    status = "OK" if result["success"] else ("TIMEOUT" if result["timeout"] else "FAILED")
    print(f"  [{status}] {result['role']}: exit={result['exit_code']} "
          f"elapsed={result['elapsed_s']}s")
    if not result["success"]:
        stderr_preview = result["stderr"][:200] if result["stderr"] else "(no stderr)"
        print(f"         stderr: {stderr_preview}")


def _get_revision():
    result = terminal(command="git rev-parse HEAD", workdir=PROJECT)

* Reviewer verdict contract

** JSON schema

Every reviewer must output a single JSON object as the final content before exit. The orchestrator parses this JSON mechanically — it never scans prose for verdicts.

#+begin_src json
{
  "verdict": "APPROVE | REQUEST_CHANGES",
  "revision": "<git sha>",
  "evidence": "<concise summary of what was verified>",
  "findings": [
    {
      "id": "C1",
      "owner": "test-designer | implementer | both",
      "requirement": "<requirement text or invariant>",
      "location": "<file:line>",
      "evidence": "<concrete observation or reproduction command>",
      "why": "<why it matters>",
      "required_outcome": "<outcome, not prescribed implementation>"
    }
  ]
}
#+end_src

** Rules

- =verdict= is required. =APPROVE= only when =findings= contains no blocking items.
- =revision= is required. If it does not match the orchestrator's expected revision, the verdict is stale and treated as =REQUEST_CHANGES=.
- =findings= may be empty (clean approval). Every finding must include all fields.
- Structural reviewers must also include =duplicate_of= in findings when applicable.
- Malformed, missing, or non-JSON output is =REQUEST_CHANGES= — fail closed.

** Verdict examples

Clean approval:
#+begin_src json
{
  "verdict": "APPROVE",
  "revision": "abc1234f",
  "evidence": "All 12 tests pass. Each requirement has coverage. RED was verified before implementation. No test games or bypasses detected.",
  "findings": []
}
#+end_src

Changes requested:

  "revision": "abc1234f",

* Review and repair protocol

** Verdict contract

Each reviewer output is parsed as JSON. The following outcomes are possible:

| Output | Treatment |
|--------+-----------|
| Valid JSON, =verdict: APPROVE=, matching revision | APPROVE |
| Valid JSON, =verdict: APPROVE=, wrong revision | REQUEST_CHANGES (stale) |
| Valid JSON, =verdict: REQUEST_CHANGES= | REQUEST_CHANGES |
| Malformed JSON | REQUEST_CHANGES |
| No JSON found | REQUEST_CHANGES |
| Missing artifact file | REQUEST_CHANGES |
| Agent exit != 0, timeout, or no output | REQUEST_CHANGES |

An approval is valid only when it names the exact revision under review. Missing, timed-out, crashed, ambiguous, or contradictory output is =REQUEST_CHANGES=.

** Routing matrix

| Finding | Primary owner | Required replay |
|---|---|---|
| Requirement encoded incorrectly or incompletely in tests | test-designer | RED → implementer GREEN → both reviews |
| Duplicated fixture/helper/harness | test-designer | RED if behavior changes → GREEN → both reviews |
| Production behavior defect | implementer | GREEN → both reviews |
| Missing calculation/business coverage | test-designer for behavioral gap; implementer for local unit gap | RED when behavioral test changes → GREEN → both reviews |
| Missing or incorrect schema/spec/contract | implementer | GREEN → both reviews |
| Production duplication or misplaced abstraction | implementer | GREEN → both reviews |
| Cross-cutting mismatch between test contract and implementation boundary | both, test designer first | RED → GREEN → both reviews |

Reviewers do not repair their own findings. After any test or code change, previous approvals are stale. Both reviewers inspect the complete new revision; approval cannot be patched forward from an older diff.

* Model selection strategy

Different models have different tool-use reliability, context-window size, and reasoning depth. Assign models to roles based on their characteristics:

| Role | Needs | Suggested tier | Example models |
|------+-------+----------------+----------------|
| test-designer | Code generation, test patterns, tool use | Mid-tier | deepseek-v4-flash, claude-haiku, gpt-4o-mini |
| implementer | Deep reasoning, ACD refactoring, multi-file edits | Strong | deepseek-v4-pro, claude-sonnet-4, gpt-4o |
| correctness-reviewer | Thorough analysis, edge cases, large context | Strong | claude-sonnet-4, gpt-4o, deepseek-v4-pro |
| structural-reviewer | Pattern matching, codebase search, large context | Strong | claude-sonnet-4, gpt-4o, deepseek-v4-pro |
| flow-documenter | Diagram generation, documentation | Mid-tier | deepseek-v4-flash, claude-haiku |

When switching a role's model:

1. *Context window*: Smaller windows need trimmed context-injection instructions.
2. *Tool reliability*: Flash/light models may need more explicit tool-use guidance.
3. *Reasoning depth*: Pro/opus models handle open-ended analysis; flash models need more structure.
4. *JSON compliance*: Reviewers on weaker models may need explicit JSON schemas in their prompts. If a model consistently produces malformed JSON, demote it from reviewer roles.

* Definition of done

A workflow is done only when all statements are true:

- Original requirements are durably recorded.
- Independent behavioral tests map to requirements.
- RED was observed for the intended missing behavior.
- Relevant tests and checks are GREEN after implementation.
- Calculation/business behavior has meaningful coverage.
- Important data boundaries have appropriate specs, schemas, types, or validation.
- Test and production duplication were actively searched for and addressed appropriately.
- Correctness and structural reviewers approved the same current revision via valid JSON.
- No code changed after those approvals.
- The Draw.io diagram represents the final approved implementation and was validated.
- Durable workflow state records artifacts, commands, verdicts, decisions, and completion.

* Setup checklist

1. Run =org-babel-tangle=. It generates all =hermes_pipeline/= files.
2. Ensure each configured model is available via the declared provider.
3. Edit =.hermes/pipeline/config.yaml= to match the project's model preferences and turn budgets.
4. Verify =hermes chat --help= confirms =--query-file=, =--oneshot=, =--worktree=, =--run-budget=, =--reasoning=, =--toolsets= are accepted.
5. Pilot on a small behavior change and inspect RED evidence, JSON verdicts, routing, dual approvals, and Draw.io output before broad adoption.
6. For parallel reviewer execution, set =reviewer_parallel: true= in config — reviewers will auto-isolate via =--worktree=.
